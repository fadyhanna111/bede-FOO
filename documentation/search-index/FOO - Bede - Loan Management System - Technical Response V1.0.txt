BEDE LMS
Sprint 2
Deliverables
Deliverable Area Description Summary
Project Kickoff & Governance 
Setup
Initiation of the engagement including the kickoff workshop, project charter, governance model, RACI, communication plan, and
risk/issue logs. Establishes the PMO tooling (Jira, Slack, shared drive) and confirms stakeholder roles on both sides before any
discovery or design work begins.
Business Requirements 
Document (BRD) - Capped
Structured requirements gathering through workshops with BEDE business teams to document the full post-disbursement lifecycle, 
product configuration parameters, and business rules for aging, penalties, settlement, and restructure. Culminates in a signed BRD 
that locks the functional scope before SRS work begins.
System Requirements 
Specification (SRS) & Test 
Cases
Translation of the signed BRD into a technical specification covering screen-level specs for custom LMS portal changes, and QA test 
cases reviewed with BEDE. Acts as the formal build contract and is signed off before implementation starts.
Dev / UAT / Prod Environment 
Setup on AWS
Full AWS infrastructure provisioning across four environments using EKS. Includes HA networking, CI/CD pipelines, Kubernetes 
hardening, container security scanning, FOO observability stack (logging, monitoring, security).
FOO LMS Core Configuration
Baseline deployment and configuration of FOO LMS including organisation structure, offices, BHD currency, chart of accounts, loan 
product templates for flat-rate and reducing-balance variants, maker-checker permissions, role-based access, and the holiday 
calendar. Provides the out-of-the-box foundation before Shariah customisation begins.
Murabaha Financing Type & 
Terminology
Extension of the LMS with a Murabaha-specific data model (cost, profit, selling price), validation rules, and UI/API relabeling of 
"Interest" to "Profit" across loan product forms, schedules, and transaction responses. Makes FOO LMS a Shariah-compliant system
while leveraging its native calculation engine.
Commodity Trading Platform 
Integration - Capped
Integration layer that captures the commodity contract reference at loan creation, fetches deal information from the external
commodity platform, and persists contract ID, product details, purchase/sell dates, and trading status as extended attributeson
each financing agreement. Includes a commodity block on the loan details screen.
Core Accounting System 
Integration - Capped
API-based posting of accounting entries from LMS to BEDE's core accounting system for all portfolio events, disbursement, accrual, 
collection, settlement, reversal, and write-off, with GL account mapping, error handling and retries, and a reconciliation log between 
the and the core accounting ledger.
CRM Integration (One-way 
Customer Read) - Capped
One-way read of customer profile data from the CRM into the LMS portal for display during loan operations and agreement lookup. 
The CRM remains the master source of customer data, bidirectional synchronisation is explicitly not implemented per client direction.

=== PDF PAGE 14 ===
BEDE LMS
Sprint 2
Deliverables
Deliverable Area Description Summary
Payment Gateway Integration 
- Capped
Inbound processing of repayments via payment gateway events and webhooks, including automatic installment allocation, payment
confirmation handling (including cheque-clearing status updates passed through from upstream systems), and a reconciliation log 
between gateway transactions and loan payments.
APIs Exposed for BEDE 
Backend
REST APIs exposed by the LMS to BEDE's backend services for loan data, schedules, transactions, and restructured-offer retrieval. 
Includes API authentication, rate limiting, and error code handling. The mobile app consumes these through BEDE's existing 
backend, there is no direct app-to-LMS contract.
Insurance Handling within 
Installment (EMI)
Custom scheduling logic that treats insurance as a recurring charge amortised equally across the loan tenure and includes it within 
the displayed EMI alongside principal and profit. Insurance is managed internally with no external insurer integration, no separate 
accounting entries, and no dedicated insurance reporting.
VAT & Fee Configuration 
Engine
Extension of FOO LMS Tax Groups to support VAT-exclusive calculation on all fee types with configurable rates over time, flexible fee 
definitions (fixed, percentage, one-time, recurring), variable fees with a hard cap (e.g., BD 100), and dedicated fee types for 
cheque-based surcharges.
Aging, Delinquency & NPA 
Handling
Configuration of DPD buckets from 1–30 days up to 36 months, automatic cessation of profit accrual at 90+ DPD, inclusion of legal 
fees and aging penalties in the customer's total outstanding balance, and tracking of the maximum delinquency reached by each
customer over the product's lifetime.
Receivable & Deferred Profit 
Tracking
Dedicated reporting module tracking movement of deferred profit (charged, reversed, new disbursements) and the receivable 
balance (disbursements, repayments, reversals, write-offs) at the individual agreement level, with real-time visibility of outstanding 
principal, accrued profit, and unearned profit at any point in time.
Early & Partial Settlement 
Engine
Automated settlement quote calculation covering outstanding principal, pro-rata accrued profit, and applicable fees. Supports fixed, 
percentage, and variable-with-cap fee structures plus cheque-based surcharges. Allows customers to pay one or multiple future 
installments in advance, with auto-closure once all balances are cleared.
Customer Exposure Limit & 
Multi-Loan Handling
Custom validation hook at the loan origination API enforcing a configurable global exposure limit per customer across all active
products in real time. Supports multiple concurrent financing agreements per customer with separate installment schedules foreach, 
aggregated against the exposure cap.

CBB & AAOIFI FAS Regulatory 
Reports - Capped (20 Reports)
Custom reports aligned with Central Bank of Bahrain regulatory templates and AAOIFI FAS-compliant reporting requirements 
(provisioning, deferred and earned profit recognition). Delivered as standard data exports (CSV/Excel) suitable for manual CBB 
submission, no direct system-to-system API integration to CBB.
Real-Time Dashboards & 
Customer Statements
Management and finance dashboards with real-time data refresh (receivables, deferred profit, portfolio yield, delinquency rates,
disbursement KPIs), branded PDF customer statement generation on demand, and file-based reconciliation reports against 
inward/outward bank movements.
Legacy LMS Data Migration & 
Cutover - Capped
End-to-end migration of up to 10,000 active loan agreements plus required history from the legacy system into FOO LMS. Includes 
mapping rules, ETL scripts, data cleansing and transformation, two rehearsal cycles, post-migration reconciliation report, and 
production cutover support with optional parallel run.
UAT Deployment & Support
UAT environment deployment, formal deliverable walkthrough with BEDE, FOO-led System Integration Testing and E2E test 
execution, and support through two defect-fix cycles during BEDE's user acceptance testing window. BEDE owns test execution and 
testers mobilisation.
Security Hardening & VA/PT 
Support
Security hardening of AWS infrastructure (container layer, network, IAM), role-based access control review, and support for one 
third-party VA/PT audit exercise including remediation of valid findings within the capped effort.
Production Deployment & Go-
Live
Orchestrated production deployment with a documented runbook, single go-live cutover window, FOO-led production E2E testing, 
and handover to post-live hypercare support. All UAT defects must be resolved and signed off before cutover.
Training, Hypercare & Post-
Live Support User guide documentation, remote client training sessions (up to 5 MDs), formal support handover, and a post-live support.

=== PDF PAGE 36 ===
Capped Efforts
Throughout this document, multiple activities are labeled as 
capped to X MD (man days). 
This indication highlights the importance of a predetermined 
limit on the amount of time and efforts that will be spent on a 
particular task. This concept is often used for activities whose 
costs cannot be accurately estimated and can vastly vary 
from an implementation to another. 
The key aspects of capped estimates lie in:
• Fixed Budget: There is a capped / maximum budget 
allocated for the specified effort, beyond which the client 
will be charged.
• Defined Scope: The tasks under capped efforts are clearly 
defined, ensuring that any amendments on the scope will 
require additional charges.
• Transparency: While some activities can be clearly defined 
and estimated, others remain high level up until the 
implementation phase where some business and technical 
decisions get clearer, the reason why FOO remains 
transparent vis-a-vis the client by capping such activities.
Project 
Deliverables

=== PDF PAGE 37 ===
For instance, capped efforts are usually mentioned for activities such as:
• Requirements Gathering & Scoping Activities: The requirements 
gathering phase might vary a lot in terms of timeline and effort based 
on the parties involved in this exercise, the readiness and maturity of 
the requisites.
• Integration Activities: The implementation of integration layers 
between FOO Backend Components and other 3rd party systems can 
only be high level estimated since all detailed technical documents for 
the 3rd party APIs are missing during the writing of this document. 
Many variables can highly increase these tasks such as: 3rd party 
APIs accessibility, connectivity, discovery, and testing.
• UI/UX Activities: User journeys and design, when applicable, are 
highly subject to change based on multiple Q&A sessions with the 
client. Hence, such activities are limited in terms of iterations and 
capped in terms of efforts.

We use a centralized log management tool built to open standards. 
The tool’s connectivity and interoperability seamlessly collect, enhances, 
stores, and analyzes log data. 
Coupled with a logs analysis tool (for gathering the logs from multiple 
servers), the log management tool can parse the logs in real time and 
send alerts if a certain predefined pattern occurs.
The log management tool is to be installed on an independent server and 
an instance of the log analysis tool to be installed on all the servers that 
need to be monitored.
Logging

=== PDF PAGE 56 ===
Use cases
• Code Exceptions 
The tool can read application logs. 
We can set a specific pattern so that we would be alerted by email in case 
exceptions occur. 
for example, if a certain exception appears in the logs 5 times in 1 minute 
this could mean that there is something about to go wrong. 
It can also be configured to send an alert for certain types of exceptions.
• System logs
The tool can log and monitor all system logs to identify the following:
• Successful ssh login attempts
• Failed ssh login attempts
• sudo access or root access
• File Monitoring 
The tool can monitor the files to detect and alert on any change on 
monitored files like server or application configurations.
• Log querying
The tool has a GUI used to query the logs and it manages indices to be 
able to query base on certain parameters (e.g. user, device, request id, 
transaction id.)
